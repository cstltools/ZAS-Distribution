## Summary of confirmed (non-speculative) performance-relevant facts

- Every non-dedicated-SP read on this page (dropdown loads, invoice search) is routed through one generic stored procedure, `ExecuteAllSqlQueryByStoreProcedure(@Query nvarchar)`, which receives the entire dynamic SQL text as a single string parameter — confirmed at `Library.DAL/InternalCls/ClsCommonInternalDAL.cs:296-317,608-629` and used by nearly every `DataContainerDataTable`/`LoadDropDownValue*` overload. This structurally prevents SQL Server from caching an execution plan per distinct *logical* query, since each call is (from the optimizer's point of view) a new ad-hoc batch wrapped inside the same outer SP call.
- The live payment-save path (`SaveCustPaymentNew2`) is fully synchronous and serial: `3N + 1` round trips for N selected invoices, with no batching, no `TVP`/table-valued-parameter usage, and no async ADO.NET calls anywhere in the chain.
- `sp_Sales_CustomerPaymentPosting` performs an unconditional, payment-unrelated `UPDATE` against `tblPaymentTranscationMaster` on every single invocation (confirmed in its recovered body) — this runs once per selected invoice on every save, not once per submission.
- `sp_MRCP_MoneyReceiptMasterInsert`'s receipt-number generation is a same-day `COUNT(*)`-based sequence, recalculated from scratch on every call.
- The print-preview join uses a `LIKE`-against-CSV-column pattern instead of a normalized join key, precluding index-seek behavior on that join leg.

No load testing, query-plan capture, or production timing data was available or collected. All "P1/P2/P3" risk ratings in this document reflect structural code-level risk (unbounded N, serial round trips, non-sargable join predicates, plan-cache-defeating indirection), not measured impact.
