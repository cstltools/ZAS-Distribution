Status of every test defined in the remediation plan (§20) and the implementation request (TMT-REG-001…012), **actually executed** against a live, user-authorized staging instance.

## Environment

- **Target:** `TOWSIF\MSSQLSERVER2019` (local SQL Server 2019 instance), database `SalesRollDB_ZAS`, with `CSTL_ERPDB` and `CSTL_ACCDB` present on the **same instance** (confirmed via `sys.databases`) — so the migration's cross-database writes are local, not MSDTC-promoted, in this environment.
- **Authorization:** the user was explicitly asked whether to treat this connection as staging and execute the migration + live tests against it, and answered **"Yes, treat it as staging."** This is documented so the live-execution decision is traceable to an explicit choice, not an assumption.
- **Tooling:** `sqlcmd.exe` (present on PATH), invoked directly via Bash. No ORM/application layer was used for these tests — the stored procedures were called directly with `EXEC`, mirroring exactly what `TradeMaterialTransferDal.cs` does.
- **Test data isolation:** all tests used a dedicated, clearly-marked test product/location (`FromProductCode='374014'`, `FromLocationId=33` — an existing product/location combo already carrying two real `tblDCStore` batch rows, `70551` and `78641`, 5 units each, chosen because it was small enough to exercise exact-stock and insufficient-stock scenarios deterministically) and fictitious `FromProductId=999001` / `ToItemDescriptionId=999002` / `EntryBy='remediation-test*'` / `Remarks` values so every test row is identifiable and attributable after the fact. **These two real `tblDCStore` rows were intentionally and permanently consumed by this test run** (10 units total, from 10 down to 0) as part of authorized regression testing — this is real inventory data, not a sandboxed copy, per the user's explicit go-ahead.

## Live definition drift discovered

The first draft of the migration script was written against `docs/database/stored-procedures-part2.md`. Pulling the actual live definition via `OBJECT_DEFINITION()` before deployment showed the **deployed** `sp_Process_TradeMaterialTransferFullProcess` is materially different from the documented one: it already contains a FIFO multi-batch cursor loop (`ORDER BY ExpDate ASC, DCStoreId ASC`) over `tblDCStore` and a three-step weighted-average rate fallback chain, neither of which appear in the documentation. The migration script was **rewritten against the live body** before deployment — see `database/migrations/2026-09-09_TradeMaterialTransfer_Idempotency_And_StockSafety.sql`'s header comment for the full explanation. `spInsertTradeMaterialTransfer`'s live definition matched the documentation exactly (verified the same way) — no drift there.

This also **resolves** the "BUSINESS RULE REQUIRED — STOCK ROW SELECTION/FIFO" stop-point from the first implementation pass: the live code already has an established order (FIFO by `ExpDate`), so per instructions it was preserved, not replaced with an invented rule.

## Deployment

Both procedures were altered via `sqlcmd -i database/migrations/2026-09-09_TradeMaterialTransfer_Idempotency_And_StockSafety.sql` against `TOWSIF\MSSQLSERVER2019` / `SalesRollDB_ZAS`. One syntax error was caught and fixed before a clean deploy: `RAISERROR` does not accept an inline `CONVERT(...)` expression as a substitution argument — fixed by assigning it to a local variable first. Post-deploy, `OBJECT_DEFINITION()` was queried again to confirm both procedures now contain the new guard logic (`ISNULL(ApprovalStatus, ...)` claim-gate text present; `UPDLOCK, HOLDLOCK` text present).

## Concurrency test limitation (honest disclosure)

REG-003 and REG-010 were executed as two separate OS-level `sqlcmd` processes launched one after the other within the same tool-call turn, not two threads guaranteed to issue their first network packet at the same instant. In both cases, the *evidence* is consistent with the guard working exactly as designed under contention (one full success, one clean no-op; two distinct sequential codes) — but because the two invocations were not observed to be mid-flight at the same moment, this is not a rigorous proof that the row-lock-based serialization holds under a true simultaneous race (e.g., two requests arriving within the same millisecond under production load). The locking mechanism itself (ordinary SQL Server row/range locks on `UPDATE`) is a well-established, standard behavior independent of this specific test's timing — but a stronger concurrency proof (e.g., a small load-testing harness issuing genuinely parallel connections, or SQL Server Profiler/Extended Events capturing lock waits) is recommended before treating this as fully proven under production-level concurrent load.
