## 1. Executive Summary

`PaymentTranscationNew2.aspx` is the live money-receipt entry screen; its wired save handler is `saveButton_ClickNew` → `PaymentTranscationDal.SaveCustPaymentNew2`. Contrary to the class/table naming (`PaymentTranscationDal`, `tblPaymentTranscationMaster/Detail`), the actual stored procedures this live path calls (`sp_PMNT_CustomerPaymentMasterInsert`, `sp_PMNT_CustomerPaymentDetailInsert`) write to **`tblCustomerPay`/`tblCustPayDetail`** — the same tables used by the older `CustomerPayment.aspx` ("path A") flow. This is a material, previously-undocumented correction to the codebase's own naming and to `docs/audit/reconciliation-audit.md`'s two-separate-schemas model (see §11).

The save flow performs 3–4 sequential, individually-autocommitted stored-procedure calls per selected invoice line with no shared transaction, and a final money-receipt insert outside that scope entirely. Failure partway through is only partially compensated (one manual `DELETE`), so a multi-invoice submission can end up with some invoices fully posted and others silently dropped, and the user is told nothing that lets them tell the two states apart. A second, more severe, previously-unidentified defect was found directly in the code: the code-behind writes `detail.CustomerMasterId` **twice**, the second write overwriting the correct customer id with the selected **BatchId** — every payment master row saved through this screen is being written with a corrupted `CustomerMasterId` (see §11). Stored-procedure-level 30/300-second duplicate guards exist (found in repo SQL, not assumed), but they are check-then-insert with no unique constraint, and their "duplicate detected" outcome (return 0) is silently swallowed by the C# loop with no user notice and no compensation.

## 7. Money Receipt Flow

1. `SaveCustPaymentNew2` loops per invoice; only on `detailResult > 0` is the `CustPayDetailId` collected into `savedDetailIds`.
2. After the loop, if `savedDetailIds.Count > 0`, a single call to `sp_MRCP_MoneyReceiptMasterInsert` is made with a CSV string of all successfully-saved detail ids (`@CustPayDetailsId`).
3. **Recovered SP body** (`docs/database/stored-procedures-part2.md:6494-6556`): the procedure itself has a 30-second duplicate guard — `IF NOT EXISTS (... CreateBy = @CreateBy AND MonyReceiptDate = @MoneyReceiptDate AND DATEDIFF(SECOND,CreateDate,GETDATE()) < 30)`. If a "duplicate" is detected it returns `@MoneyReceiptID = 0` **without inserting** — even though the underlying `tblCustomerPay`/`tblCustPayDetail` rows for this submission were already committed in step 1–2 (separate autocommits, already done). Receipt number format: `RCPT-` + 2-digit year + `MMdd` + `(1000 + count-of-receipts-created-today)` — a same-day, non-atomic `COUNT(*)`-based sequence (race condition risk under concurrent submits within the same second/transaction window: two concurrent calls can compute the same `@ProCount` and generate duplicate receipt numbers before either INSERT commits, since there is no `SERIALIZABLE`/`UPDLOCK` hint or unique constraint shown in the recovered body). **Confirmed by code; concurrent-collision confirmation itself is UNKNOWN — no live DB.**
4. Code-behind: `moneyReceiptId <= 0` (whether from a genuine failure or from the SP's own dup guard) triggers `GetMoneyReceiptByUser(loginName)` — `SELECT TOP 1 ... WHERE CONVERT(DATE,CreateDate)=today AND CreateBy=<user> ORDER BY MoneyReceiptId DESC` (`PaymentTranscationDal.cs:564-577`) — i.e. **whatever receipt this user created most recently today, which may belong to a completely different transaction**, is then shown as "invTextBox"/printable, alongside the message `"❌ Data Already Exist. Please print & check !"`. This message is misleading: the underlying condition can be (a) a genuine transient duplicate (harmless — the real receipt already exists and is what's shown), or (b) `savedDetailIds.Count == 0` because every detail insert failed/deduped, in which case **no receipt was created for this submission's payments and the fallback shows an unrelated receipt** with no way for the user to distinguish the two cases. **Confirmed by direct code read (`.aspx.cs:531-544`), inference on user impact.**

## 8. Transaction Boundary

**Confirmed fact:** No explicit `SqlTransaction`/`TransactionScope` exists anywhere between `saveButton_ClickNew` and any of the SP-calling helper methods (`SaveAction`/`UpdateAction`/`DeleteAction` → `ExecuteNonQueryAction`, `ClsCommonInternalDAL.cs:801-865`). Each call creates its own `Database` via `DatabaseFactory.CreateDatabase(...)` and issues one `ExecuteNonQuery`. Each of the recovered SP bodies (`sp_PMNT_CustomerPaymentMasterInsert`, `sp_PMNT_CustomerPaymentDetailInsert`, `sp_MRCP_MoneyReceiptMasterInsert`, `sp_MRCP_DeletePayment`, `sp_Sales_CustomerPaymentPosting`) contains **no `BEGIN TRAN`/`COMMIT`/`ROLLBACK`/`TRY`/`CATCH`** — confirmed by reading their full bodies in `docs/database/stored-procedures-part2.md` and `-part3.md`.

Per invoice line, the true sequence of independently-committed statements is:
1. INSERT `tblCustomerPay` (autocommit)
2. INSERT `tblCustPayDetail` (autocommit) — or, if this SP's own 30s dup guard fires, a **no-op** that returns 0
3. IF (2) failed/deduped: DELETE `tblCustomerPay` + `tblCustPayDetail` for that CustPayId (autocommit) — a manual, application-level compensating action, not a DB rollback
4. IF (2) succeeded: `sp_Sales_CustomerPaymentPosting` (autocommit; several INSERT/UPDATE statements inside it, none transactionally wrapped even within that one SP)
Then, once, after the whole loop: INSERT `tblMoneyReceipt` (autocommit).

There is a real window between steps 1 and 3 where the `tblCustomerPay` row is live and visible to any concurrent reader (reports, other sessions) before being deleted. **Confirmed by code; observing the window in a live system is UNKNOWN/NOT TESTED.**

## 9. Failure/Partial Commit Analysis

- `detailResult <= 0` (real insert failure **or** the SP's own 30-second dup guard) → `DeletePaymentMasterInfoNew(custPayId)` compensates that one master row, sets `allSaved = false`, then **`break`s out of the entire loop** — remaining, not-yet-processed invoices in the same submission are never attempted. Invoices processed in earlier loop iterations remain fully committed (master + detail + journal posting already ran). **Confirmed by direct code read (`PaymentTranscationDal.cs:122-138`).**
- `allSaved` is set but **never read anywhere** in `SaveCustPaymentNew2` or its caller — it is dead state, computed and discarded. **Confirmed.**
- `PaymentJournalPosting`'s `bool` return value is discarded (`PaymentTranscationDal.cs:134`, statement result not assigned/checked). If `sp_Sales_CustomerPaymentPosting` throws, `ExecuteNonQueryAction`'s catch block (`ClsCommonInternalDAL.cs:860-864`) re-throws (`throw ex;`) — this would actually surface as an unhandled exception up through `UpdateAction`'s own catch (`ClsCommonInternalDAL.cs:663-667`, which *does* catch and logs via `ClsErrorLogger.Log`, returning `false`) — so a thrown/failing journal posting is swallowed at the `UpdateAction` layer and the boolean `false` is silently discarded by the caller. **Net effect, confirmed by code: a payment can be fully recorded in `tblCustomerPay`/`tblCustPayDetail` while its accounting journal entry silently fails to post, with no error surfaced to the user, no retry, and no flag set anywhere for later reconciliation.**
- If `savedDetailIds.Count > 0` but `sp_MRCP_MoneyReceiptMasterInsert` returns 0 (its own 30s dup guard, or a genuine failure), the function returns `status = 0` even though every payment/detail/journal-posting call in the loop already committed. The code-behind's `else` branch (§7) then shows the wrong receipt with a misleading message. **This is the single most severe failure mode identified: money can be received/recorded and posted to accounting with no receipt document generated for it, and no user-facing signal that this specific case occurred.**

## 10. Duplicate/Concurrency Analysis

- **Client side:** `saveButton`'s actual `OnClientClick` is `return confirm('Are you sure you want to Save ?');` (`PaymentTranscationNew2.aspx:725`) — a plain confirmation dialog with **no button-disable, no re-entrancy guard**. The `preventDoubleClick(btn)` JS function defined in the page's `<script>` block (`PaymentTranscationNew2.aspx:264-272`, which *does* disable the button and change its text) is **defined but never referenced by any control on this page** (confirmed via grep — the only match for `preventDoubleClick` in the file is its own definition). This is a **stronger finding than "disable-on-click is not enough against network retry"**: there is currently **no client-side double-submit guard of any kind** on `saveButton`, not even the weaker disable-on-click pattern the dead JS function would provide.
- **Server side (live path):** `saveButton_ClickNew` calls no advisory duplicate check of its own (confirmed — no call to `ValidationDoble` or any equivalent exists in this method). Duplicate protection instead lives inside the stored procedures it calls:
  - `sp_PMNT_CustomerPaymentMasterInsert`: a 300-second (5-minute) check-then-insert guard on `(CreateBy, CustomerMasterId, BatchId, PaymentAmount, PaymentDate, InvoiceIdForValidation)` via `MasterProcessTime`.
  - `sp_PMNT_CustomerPaymentDetailInsert`: a 30-second check-then-insert guard on `(CustPayId, InvoiceId, PaymentAmount, AIT, Discount)` via `ProcessTime`.
  - `sp_MRCP_MoneyReceiptMasterInsert`: a 30-second check-then-insert guard on `(CreateBy, MonyReceiptDate)` via `CreateDate`.
  All three are **classic TOCTOU** (`IF NOT EXISTS(...) BEGIN INSERT ... END`) with no `UPDLOCK`/`HOLDLOCK`/`SERIALIZABLE` hint visible in the recovered bodies and no unique constraint backing the check — two requests arriving within the same few milliseconds can both pass the `NOT EXISTS` check before either commits. **Confirmed by recovered SQL text; whether this race is exploitable in the live SQL Server's actual isolation level is UNKNOWN/NOT TESTED.**
  - When any of these guards fires (returns 0 / `@CustPayId=0` / `@CustPayDetailId=0` / `@MoneyReceiptID=0`), the C# caller treats it identically to a hard failure — no distinction is made between "genuine duplicate, safe to ignore" and "real insert error." For the master/detail case this triggers the compensating delete + loop `break` (§9); the money-receipt case falls through to the misleading "Data Already Exist" branch (§7).
- **Legacy path only** (`saveButton_Click`, unreachable per §3): calls `ValidationDoble(invoiceId)` — a raw-SQL `SELECT` over a `±5`-minute window, purely advisory, no lock. P4 given the path is dead code, but documents the intended (and equally TOCTOU) pattern this codebase generally uses for dedup.

## 11. Master/Detail Integrity

**Finding MD-1 (confirmed, "master per detail" behavior):** `SaveCustPaymentNew2` creates one **new** `tblCustomerPay` row per selected invoice/detail, not one master row shared by N details. `aCustPayment.PaymentAmount` (and `.CustomerMasterId`, `.BatchId`, `.PayType`) are reassigned from the current `custPaymentDetail` on every loop iteration (`PaymentTranscationDal.cs:103-111`) before `SaveCustomerPaymentMaster` is called — so for a 3-invoice submission, three separate `tblCustomerPay` rows are created, each holding that one invoice's amount, not the submission's total. The "master/detail" naming and the 1:N `CustPayId → tblCustPayDetail` foreign-key shape therefore do not reflect a real N-detail-per-master submission in the live path; it is a **flattened one-master-per-invoice-line model wearing a master/detail schema**. Downstream consumers that assume `tblCustomerPay.PaymentAmount` reflects a full multi-invoice receipt total would be wrong.

**Finding MD-2 (new, confirmed — not previously documented):** In `saveButton_ClickNew` (`.aspx.cs:473-479`), building each `CustPaymentDetail`:
```csharp
detail.CustomerMasterId = !string.IsNullOrWhiteSpace(Convert.ToString(key["CustomerMasterId"]))
   ? Convert.ToInt32(key["CustomerMasterId"])
   : 0;

detail.CustomerMasterId = !string.IsNullOrWhiteSpace(Convert.ToString(key["BatchId"]))
  ? Convert.ToInt32(key["BatchId"])
  : 0;
```
The second assignment **overwrites `detail.CustomerMasterId` with the row's `BatchId` value** instead of assigning it to `detail.BatchId` (which exists as a separate property on `CustPaymentDetail`, `Library.DAO/SInventory_Entities/CustPaymentDetail.cs:19`, and is left at its default `0`). Because `SaveCustPaymentNew2` sets `aCustPayment.CustomerMasterId = custPaymentDetail.CustomerMasterId` and `aCustPayment.BatchId = custPaymentDetail.BatchId` on every iteration (`PaymentTranscationDal.cs:105-106`), the master row's real customer id (correctly captured earlier from `hdCustomerId.Value` at `.aspx.cs:436-438`) is **clobbered before the save call** and replaced with the selected batch id, while `BatchId` is always written as 0. **Every payment saved through this screen has `tblCustomerPay.CustomerMasterId` populated with a batch id (or 0), not the real customer, and `BatchId` populated with 0 regardless of the actual batch.** This directly undermines the 300-second dedup key in `sp_PMNT_CustomerPaymentMasterInsert` (which includes `CustomerMasterId`/`BatchId`) and would corrupt any customer-ledger/AR report that ever starts reading `tblCustomerPay.CustomerMasterId` for rows created via this screen. **Confirmed directly from source (`.aspx.cs` + `CustPaymentDetail.cs`); this is a genuine bug, independent of the transaction/dedup findings above.**

**Finding MD-3:** `sp_Sales_CustomerPaymentPosting` recomputes `tblInvoice.PaymentAmount/AIT/DiscountOnPayment` by `SUM`-aggregating **all** `tblCustPayDetail` rows for `@InvoiceId` (not filtered by `@CustPayId`) — so the update is idempotent with respect to which specific `CustPayId` triggered it (re-running it for the same invoice recomputes the same total), but it also means the `@CustPayId` parameter passed in is otherwise unused in that specific UPDATE. **Confirmed by recovered SP body.**

## 12. Accounting Integration

- Confirmed: `PaymentJournalPosting` → `sp_Sales_CustomerPaymentPosting(@CustPayId, @InvoiceId)` is the only accounting-posting call in this page's live save path.
- Confirmed (recovered body): the procedure (a) bulk-rejects stale, unrelated `tblPaymentTranscationMaster` rows older than today that are still `IsProcess=0, IsReject=0` — an incidental side effect unrelated to the current payment, (b) recomputes `tblInvoice` payment aggregates from `tblCustPayDetail`, (c) opens a cursor over customer/company/financial-year/chart-of-accounts data across `CSTL_ACCDB`/`CSTL_ERPDB`/local tables and inserts Dr/Cr rows into `CSTL_ACCDB..tblDebitCreditVoucherMaster/Detail`.
- Per `docs/audit/accounting-integration-audit.md:73,105-109`: this is one of only two call sites in the whole codebase where the C# layer supplies real accounting decisions (`AIT`, `BankAccId`, `CashAccId`, `Discount`, `PaymentAmount` — passed into `sp_PMNT_CustomerPaymentDetailInsert`) rather than deferring entirely to the SP; everywhere else the app passes only scalar ids and the SP decides the accounting shape internally.
- Return-value handling: as documented in §9, the boolean result of the posting call is discarded by the immediate caller and any failure inside it is swallowed by `ClsCommonInternalDAL.UpdateAction`'s catch block (logs via `ClsErrorLogger.Log`, returns `false`) with **no propagation back to the UI**. **Confirmed.**
- Whether the posting SP's internal cursor logic can itself partially post (some Dr/Cr rows inserted, then an error before the rest) is **UNKNOWN** — the body has no `TRY`/`CATCH`/transaction, so a mid-cursor SQL error would abort the batch, but whether earlier iterations' INSERTs within the same batch are rolled back depends on SQL Server's default autocommit-per-statement behavior for a stored procedure without an explicit transaction: each INSERT inside the cursor loop is its own autocommit unit, so a later-iteration failure does **not** roll back earlier-iteration INSERTs. **Confirmed by SQL semantics + recovered body structure (no explicit `BEGIN TRAN`).**

## 14. Security Findings

**SEC-1 — Money receipt viewer trusts Session value with no ownership check (confirmed).** `BatchWiseMoneyReceiptReportViewer.aspx.cs` `Page_Init` (line 24) reads `Session["MoneyReceiptId"]` directly and passes it straight into `BatchWiseCollectionReportDal.MoneyReceiptById(payId)` (`BatchWiseCollectionReportDal.cs:78-117`), a string-concatenated `SELECT ... WHERE MoneyReceiptId = <payId>` with **no `WHERE` clause tying the result to the logged-in user, their company/unit, or any session-scoped customer/permission filter**. There is no re-validation of "does this receipt belong to a customer/company this user is allowed to see" anywhere in this call chain.
- **Attack surface:** `Session["MoneyReceiptId"]` is set only by `PopupReport()` in `PaymentTranscationNew2.aspx.cs:1499-1507`, from `rptInvoiceId.Text` — a server-side `asp:Label` with `Visible="False"`. Because ASP.NET WebForms does not render output for a control with `Visible="False"`, its value is not present in the delivered HTML and is not directly editable via view-source; however, Label `Text` is still tracked in the page's `__VIEWSTATE` unless view-state is explicitly disabled for that control (not observed to be disabled here), so the value is present (MAC-protected, not necessarily encrypted unless `viewStateEncryptionMode` is configured — **UNKNOWN, not found in `Web.config`** in this investigation) inside the postback payload. **Direct URL/querystring tampering of `MoneyReceiptId` on the report-viewer page itself is not possible from this page's own flow** (the viewer takes no querystring parameter for it, only Session), but this is a per-application-instance Session key with no additional scoping (e.g., not `Session["MoneyReceiptId_" + userId]`) — **whether any *other* page in the application sets `Session["MoneyReceiptId"]` to a value influenced by the current or a different user without an ownership check is UNKNOWN** (out of scope for this investigation, which was scoped to `PaymentTranscationNew2.aspx`); if any other page does so from user-controlled input, this would be a directly exploitable IDOR. As it stands from this page alone, the practical exploit path is limited, but the report viewer's total absence of a server-side ownership/company check is itself a defense-in-depth gap: any code path (current or future) that sets this Session key opens full IDOR with zero additional work. **Confidence: confirmed code fact for "no ownership check exists"; confidence on practical exploitability from this page alone is medium (requires either view-state tampering feasibility or another vulnerable Session-setter, neither confirmed here).**
- **SQL injection surface:** `MoneyReceiptById(string moneyReceitId)` concatenates `moneyReceitId` directly into SQL with no parameterization and no type check before the query executes (the C# converts elsewhere with `ToString(CultureInfo.InvariantCulture)` of an `int`, but the DAL method itself accepts a raw string and does not re-validate it as numeric) — from this page's own flow the value always originates from a server-generated int, so it is not attacker-reachable via this specific call chain, but the method itself is unsafe by construction and would become an injection point if ever called with client-supplied text.

**SEC-2 — Legacy save path SQL injection (P4, dead code but present).** `PaymentTranscationDal.SaveCustPayment(PaymentTranscationMasterDao)` (`PaymentTranscationDal.cs:286-322`) and `SaveCustDetail` (`:323-368`) build `INSERT` statements via raw string concatenation of `aCustPayment.RefNo`, `PaymentStatus`, `CreateBy`, and `aCustPaymentDetail.Remarks` — all of which trace back to free-text `TextBox` fields (`refNameTextBox.Text`, `remarksTextBox.Text`) with no escaping and no `FilteredTextBoxExtender` restricting them to safe characters (unlike `payAmountTextBox`/`aitTextBox`/`discountTextBox`, which are numeric-filtered). This is a genuine SQL-injection vector **if this legacy path is ever reachable** — confirmed unreachable from this page's current markup (§3), so rated P4 (dead-code risk) rather than P0, but flagged because the method remains callable from any other caller not audited here.

**SEC-3 — Client-side numeric filtering only, no server-side re-validation (confirmed, low severity for this page).** The `FilteredTextBoxExtender` controls restricting `payAmountTextBox`/`aitTextBox`/`discountTextBox` to `0123456789.` are AJAX Control Toolkit client-side filters; the live save path (`SaveCustPaymentNew2`) reads these values via `Convert.ToDecimal` from `DataKey` values already committed to the grid at `btnAddToGrid_Click` time, which itself only did a `decimal.TryParse` (silently defaulting to 0 on failure, `.aspx.cs:166-173`) — no explicit server-side range/format validation beyond "must parse as decimal, must be > 0 in combination" (`Validation()`, `.aspx.cs:359-419`). Not independently exploitable for injection (values are always bound as typed `SqlParameter`s in the live path), but confirms the prior spec's note that server-side re-validation of character filtering is absent.

## 16. Recommended Remediation Plan

Ordered by leverage, preserving existing business behavior except where corruption risk (P0) requires an actual behavior change:

1. **Fix `CustomerMasterId`/`BatchId` mapping bug (P0-2)** — one-line fix in `.aspx.cs:477-479`, zero behavior change to anything currently working correctly, pure bug fix. Lowest risk, highest urgency.
2. **Wire `preventDoubleClick` to `saveButton` (P1-3)** — the fix already exists in the page's own JS; just add the `OnClientClick` attribute. Zero new code.
3. **Wrap the per-submission save sequence in a transaction (P0-1, P1-1, P1-2)** — introduce a `TransactionScope` (or explicit `SqlTransaction` passed through the DAL calls) around the master/detail/posting/receipt inserts for one submission, so a mid-loop failure rolls back cleanly instead of partially committing. This is the largest-effort item and needs care because none of the called SPs currently participate in a caller-supplied transaction — would need to confirm `DatabaseFactory.CreateDatabase` connections can be shared/enlisted, or switch to `TransactionScope` with `System.Transactions` (which promotes to DTC across multiple connections — verify DTC is configured, or refactor to use one shared `SqlConnection`/`SqlTransaction` passed to each `ExecuteNonQueryAction` call).
4. **Check and act on `PaymentJournalPosting`'s return value (P1-2)** — at minimum log distinctly and flag the row; do not silently proceed.
5. **Distinguish "duplicate detected" (return 0 from a guard) from "real failure" (exception/other 0)** in the SPs' output contract (e.g., use `-1` for genuine duplicate vs `0` for hard failure) so the C# layer and UI can message correctly instead of collapsing both into "Data Already Exist."
6. **Add an ownership/company filter to `BatchWiseCollectionReportDal.MoneyReceiptById` (P2-1)** — defense in depth even though no direct exploit path was found from this page alone.
7. **Migrate dropdown/search reads off the generic `ExecuteAllSqlQueryByStoreProcedure` wrapper (P2-2)** — lower priority, performance-only, no correctness risk.
8. **Delete or fix the dead `saveButton_Click` path (P4-1)** — confirm no other page/button calls `PaymentTranscationDal.SaveCustPayment(PaymentTranscationMasterDao, ...)`/`SaveCustDetail` before deleting; if kept for some reason, fix all three defects.

## 18. Production Risk Verdict

This page is safe to keep running as-is for single-invoice, non-concurrent, happy-path usage, which is presumably its dominant real-world case. However, two confirmed, code-level defects (P0-1: money-receipt insert can silently fail after the payment is already committed, with a misleading UI message papering over it; P0-2: every payment's `CustomerMasterId` is being written incorrectly) represent active data-integrity risk that does not require any unusual conditions — P0-2 in particular fires on every normal save through this screen, not just under failure/concurrency edge cases, and should be treated as a data-corruption bug in production today (impact on already-existing rows is UNKNOWN without live-DB access, but ongoing corruption is a near-certainty given the code is unconditional). The lack of a client-side double-submit guard (P1-3) and the absence of a shared transaction across the multi-step save sequence (P0-1/P1-1/P1-2) compound risk specifically for multi-invoice submissions and for any deployment under real network latency or concurrent users. None of the failure modes here were confirmed against live data; all severity ratings above P4 are based on direct source-code and recovered-SQL evidence, not observed incidents.
