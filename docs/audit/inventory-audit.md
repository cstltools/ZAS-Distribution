# Inventory / Stock Logic Audit

Scope: `Library.BLL/SInventory_BLL`, `Library.DAL/SInventory_DAL`, `Solution.Web/SInventory_UI/*.aspx.cs`.
Read-only audit — no source, data, or schema was modified.

Baseline verified against: `specs/inventory-warehouse/README.md` and `specs/inventory-warehouse/pages/*.md`,
`specs/SPEC-GAPS.md` (`GAP-APP-004`, `GAP-APP-005`, `BR-INV-005`).

**Correction to the SPEC-GAPS baseline:** `specs/SPEC-GAPS.md` states `GAP-DB-001`/`GAP-DB-002` (stored-procedure
bodies and DB schema) are `OPEN` — no artefact in the repo. That is no longer true: `docs/database/` (added after
that spec was written) contains a schema (`docs/database/tables.md`, `views.md`, `relationships.md`) and
reverse-engineered T-SQL bodies for many procedures (`docs/database/stored-procedures-part1.md`, `-part3.md`,
`-part4.md`, `functions.md`), sourced from the live `SalesrollDB_ZAS` instance. `docs/database/stored-procedures.md`
itself is stale (still says "Body: NOT AVAILABLE" for all 119) — **the batch files are the current source of
truth, the index is not**. This audit used the batch files directly for the procedures below; anything not
found in `docs/database/*` is still marked **HUMAN VERIFICATION REQUIRED**.

Labels: **CONFIRMED** (read in source/SP body), **INFERRED** (strong circumstantial evidence), **SUSPECTED**
(plausible, not provable by static reading), **UNKNOWN** (cannot be determined at all from available artefacts).

## 2. What the recovered stored-procedure bodies actually show (resolves several would-be "HUMAN VERIFICATION REQUIRED" items)

Read directly from `docs/database/stored-procedures-part1.md` and `-part3.md`:

- **`sp_Sales_ExecuteDeliveryPipeline`** (`docs/database/stored-procedures-part3.md:3823-3831`) — "the largest single black box" per `specs/SPEC-GAPS.md`. Its body is now available: it is a two-line orchestrator that calls `sp_Process_WeightedAverageSalesConfirmation` then `sp_Sales_DeliveryCOGSPosting`. **Neither of those two nested calls' own bodies were found in the recovered batches** (`sp_Process_WeightedAverageSalesConfirmation` in particular — grepped, not present). CONFIRMED: the pipeline itself does not touch any table directly (no FROM/JOIN, no INSERT/UPDATE at its own level). **HUMAN VERIFICATION REQUIRED for `sp_Process_WeightedAverageSalesConfirmation`** — this is the one place a *second* stock-quantity mutation on `tblDCStore` could theoretically occur after the invoice-time deduction already performed by `InvoiceBLL.UpdateDCStock` (`BUG-STOCK-014`).
- **`sp_Sales_DeliveryCOGSPosting`** (`docs/database/stored-procedures-part3.md:2341-2409+`) — reads `tblDCStore.UnitPrice_CostPrice` for costing but **only writes to `CSTL_ACCDB..tblDebitCreditVoucherMaster/Detail`** (GL). CONFIRMED: does not mutate `tblDCStore.StockQty`.
- **`sp_Sales_ProductDestroyPosting`** (`docs/database/stored-procedures-part3.md:3858-3924+`) — reads `tblDCStoreFreeze`/`tblDCStore` for costing but **only writes GL vouchers**. CONFIRMED: the freeze-stock decrement for Destroy is performed **entirely in C#** (`DestroyProductDal.UpdateFreezeStockQty`), not inside this SP — so the missing negative-stock guard noted in the matrix above is a real, unmitigated gap (nothing in the SP catches it either).
- **`sp_FreezeStockPosting`** (`docs/database/stored-procedures-part1.md:13121-13200+`) — GL-only (flags `IsPosting`, posts a Debit/Credit voucher pair). CONFIRMED: does not touch `tblDCStoreFreeze.StockQty`/`tblDCStore.StockQty`. Also: **`IF(@TempCompanyId = 16) BEGIN ... END`** — the entire posting body is hard-restricted to `CompanyId = 16`; freeze transactions for every other company silently post no GL entry at all (`BUG-STOCK-013`).
- **`sp_DCStoreOpeningBalanceProcess`** — a row-by-row cursor snapshot of `tblDCStore` into `tblDCStore_OpeningBalance`, run on demand (not scheduled per period as far as the C# call sites show — worth confirming whether it is invoked more than once and whether re-running it duplicates opening-balance rows; not checked here).
- **`sp_Process_WeightedAverageSalesConfirmation`, `sp_WHStockInPosting`, `sp_Acc_MaterialConversionReceive`, `sp_Process_TradeMaterialTransferFullProcess`, `sp_FreezeStockReleasePosting`, `sp_Process_WeightedAverage`, `sp_Process_WeightedAverageB2BTransfer`, `sp_Process_WeightedAverageFreezeStock`, `sp_I_DCStockOutInfo`** — grepped across all of `docs/database/*.md`, **not found as their own documented procedure** (only referenced as nested `EXEC` calls or listed in the stale index). **HUMAN VERIFICATION REQUIRED** for each — `sp_helptext` should be re-pulled for these specific names, since the recovered batches evidently did not capture 100% of the 119 procedures.

## 3. Confirmed bugs

| ID | Title | Severity | Confidence |
|---|---|---|---|
| BUG-STOCK-001 | No stock-availability check before sales invoice save — `InvoiceBLL.UpdateDCStock` (`Library.BLL/SInventory_BLL/InvoiceBLL.cs:218-321`) silently stops allocating once FEFO batches run out; the invoice still saves with a line under-fulfilled and no error. Matches `GAP-APP-004`. | CRITICAL | CONFIRMED |
| BUG-STOCK-002 | Stock-quantity updates use a C#-computed overwrite (`SET Qty = '<value>'`) instead of an atomic `SET Qty = Qty ± x` in at least 7 methods: `InvoiceDAL.UpdateDCStoreQuantity`, `OtherStockActionDAL.UpdateDCStock`/`UpdateDCStoreFreezeStock`, `ChalanDAL.UpdateDCStockQuantity`, `StockConditionFreezeDAL.UpdateCentralStore`/`UpdateDCStore`, `WhFreezeStockReleaseDal` (both methods), `DestroyProductDal.UpdateFreezeStockQty`, `CentralStoreDAL.UpdateCurrentStockQuantity`. Concurrent transactions against the same row can silently lose one side's update. Matches `GAP-APP-005`. | HIGH | CONFIRMED |
| BUG-STOCK-003 | No `SqlTransaction`/`BEGIN TRAN` wraps any two-sided stock movement anywhere in `Library.DAL/SInventory_DAL` (grepped, zero hits besides an unused one in `DB_Manager.cs`). Every transfer/freeze/release is 2+ independently-committing ADO.NET calls; a mid-sequence failure destroys or duplicates stock (e.g. `OtherStockAction.aspx.cs:141-149`, `WhFreezeStockRelease.aspx.cs:166-222`, `StockConditionFreeze.aspx.cs` 3-step chain). | CRITICAL | CONFIRMED |
| BUG-STOCK-004 | No negative-stock guard at the SQL layer anywhere in the module — every decrement is an unconditional `UPDATE ... WHERE <key>=id` with no `AND Qty >= x`. All quantity checks found are client-side ASP.NET TextBox/grid comparisons, trivially bypassable via a direct postback that skips the triggering event (e.g. `DirectStockOut.aspx.cs` guard lives only in `quantityTextBox_OnTextChanged`, not re-checked in `submitButton_OnClick`). | HIGH | CONFIRMED |
| BUG-STOCK-005 | DC-to-DC stock transfer deducts source stock at **challan creation** (`ChalanDAL.cs:330-334`), before the destination DC confirms receipt. There is no in-transit stock bucket in `tblDCStore` — if the transfer is never received (lost, damaged, abandoned), stock is permanently gone from the source with only an unconfirmed `tblChalanInfo`/`tblChalanDetail` document as evidence. | HIGH | CONFIRMED |
| BUG-STOCK-006 | Derived-transaction date copied from parent instead of the actual event date, in two confirmed places: (a) sales-return freeze rows set `StockRcvDate` from the **original** pre-sale batch row instead of the return date — `ReturnInvoiceCreationForCustomer.aspx.cs:776`, `ReturnustomerByInvoiceApproval.aspx.cs:130-131`, `DelivaryInvoiceCreationForCustomerByOrderAuto.aspx.cs:1036,1212` (contrast with `StockConditionFreeze.aspx.cs:220,280,430,510`, which correctly sets `StockRcvDate = DateTime.Now` for an analogous new-freeze-event); (b) DC-to-DC transfer receipt sets the destination row's `tblDCStore.ReceiveDate` from the source challan's `ChalanDate` (`ChalanDAL.cs:200-209` aliases `tblChalanInfo.ChalanDate AS ReceiveDate`, consumed at `TransferReceiveProductByChalanByDC.aspx.cs:66`), misdating the destination batch's aging by however long the transfer was in transit. | MEDIUM | CONFIRMED |
| BUG-STOCK-007 | `DestroyProductApproval.aspx.cs:92-108` computes `qty = currentFreezeStockQty - StockOutQty` and writes it via `DestroyProductDal.UpdateFreezeStockQty` with **no `qty >= 0` check**. Confirmed (§2) that `sp_Sales_ProductDestroyPosting` does not guard this either (GL-only). A destroy quantity exceeding the frozen quantity silently drives `tblDCStoreFreeze.StockQty` negative. | HIGH | CONFIRMED |
| BUG-STOCK-008 | Two structurally different, inconsistent sales-return architectures: regular customer returns go through a freeze/quarantine tier requiring a manual release (`InvoiceBLL.SaveDCStoreFreeze`), while consumer-customer returns go straight back into sellable stock via an atomic increment (`CustomerReturnDAL.UpdateDCStoreQty`, `Library.DAL/SInventory_DAL/CustomerReturnDAL.cs:106-110`) with no inspection step.
